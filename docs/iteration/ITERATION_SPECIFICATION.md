# 项目迭代开发规范

## 1. 目的

规范项目迭代开发流程，确保代码质量、功能稳定性和可维护性，通过系统化的测试回归机制保证每次迭代的质量。

## 2. 适用范围

适用于项目所有开发迭代，包括但不限于：
- 新功能开发
- 功能优化和改进
- Bug修复
- 重构和代码优化
- 性能优化
- 技术债务清理

## 3. 迭代流程概述

```
需求分析 → 方案设计 → 开发实现 → 单元测试 → 集成测试 → 代码审查 → 测试回归 → 部署上线
```

## 4. 详细迭代流程

### 4.1 需求分析阶段

#### 4.1.1 需求收集
- 收集用户需求和反馈
- 分析业务需求和技术需求
- 评估需求的可行性和优先级

#### 4.1.2 需求文档
- 编写详细的需求文档
- 明确功能描述、验收标准、技术约束
- 评审需求文档并获得确认

#### 4.1.3 输出物
- 需求文档（PRD）
- 验收标准清单
- 技术约束说明

### 4.2 方案设计阶段

#### 4.2.1 技术方案设计
- 分析现有架构和代码
- 设计技术方案和实现路径
- 评估方案的风险和影响范围

#### 4.2.2 数据库设计（如需要）
- 设计数据库表结构
- 设计索引和约束
- 编写数据库迁移脚本

#### 4.2.3 API设计（如需要）
- 设计RESTful API接口
- 定义请求和响应格式
- 编写API文档

#### 4.2.4 方案评审
- 组织技术方案评审
- 收集评审意见
- 优化和完善方案

#### 4.2.5 输出物
- 技术方案文档
- 数据库设计文档
- API设计文档
- 方案评审记录

### 4.3 开发实现阶段

#### 4.3.1 开发准备
- 创建开发分支
- 搭建开发环境
- 准备测试数据

#### 4.3.2 代码实现
- 按照技术方案进行编码
- 遵循代码规范和最佳实践
- 编写清晰的代码注释

#### 4.3.3 单元测试
- 为核心功能编写单元测试
- 确保测试覆盖率达到要求
- 验证单元测试通过

#### 4.3.4 代码规范检查
- 运行代码格式化工具
- 运行静态代码分析工具
- 修复代码规范问题

#### 4.3.5 输出物
- 功能代码
- 单元测试代码
- 代码注释和文档

### 4.4 集成测试阶段

#### 4.4.1 集成测试准备
- 准备测试环境
- 准备测试数据
- 配置测试参数

#### 4.4.2 集成测试执行
- 执行集成测试用例
- 验证前后端集成
- 验证数据库操作
- 验证API接口

#### 4.4.3 问题修复
- 记录测试发现的问题
- 分析问题原因
- 修复问题代码
- 重新执行测试

#### 4.4.4 输出物
- 集成测试报告
- 问题修复记录

### 4.5 代码审查阶段

#### 4.5.1 代码提交
- 提交代码到版本控制系统
- 编写详细的提交信息
- 创建Pull Request或Merge Request

#### 4.5.2 代码审查
- 指定代码审查人员
- 审查代码质量和逻辑
- 审查测试覆盖率和质量
- 提出审查意见

#### 4.5.3 代码修改
- 根据审查意见修改代码
- 修改后重新提交审查
- 确保审查通过

#### 4.5.4 输出物
- Pull Request/Merge Request
- 代码审查记录
- 代码修改记录

#### 4.6.8 问题处理流程

##### 问题分类
- **严重问题**：系统崩溃、数据丢失、功能完全不可用
- **主要问题**：功能部分不可用、影响用户体验
- **次要问题**：界面显示问题、提示信息不准确
- **建议**：功能优化建议、用户体验改进建议

##### 问题处理步骤
1. **问题记录**
   - 记录问题详情
   - 记录复现步骤
   - 记录错误日志
   - 记录截图或录屏

2. **问题分析**
   - 分析问题原因
   - 定位问题代码
   - 评估影响范围
   - 制定修复方案

3. **问题修复**
   - 修复问题代码
   - 添加或修改测试用例
   - 验证修复效果
   - 确保没有引入新问题

4. **重新测试**
   - 重新运行相关测试
   - 验证问题已解决
   - 确保其他功能正常
   - 更新测试报告

5. **问题跟踪**
   - 使用问题跟踪系统（如JIRA、GitHub Issues）
   - 更新问题状态
   - 记录修复过程
   - 归档已解决的问题

##### 测试用例调整
- 如果测试用例本身有问题，需要调整测试用例
- 如果需求变更，需要更新测试用例
- 如果发现新的测试场景，需要添加测试用例
- 确保测试用例与实际需求保持一致

## 5. 迭代规范要求

### 5.1 代码质量要求

#### 5.1.1 代码规范
- 遵循项目代码规范
- 使用有意义的变量和函数名
- 编写清晰的代码注释
- 保持代码简洁和可读性

#### 5.1.2 代码审查
- 所有代码必须经过审查
- 审查通过后才能合并
- 审查意见必须及时处理

#### 5.1.3 测试覆盖
- 核心功能必须有单元测试
- 测试覆盖率 ≥ 80%
- 测试用例必须有效和可靠

### 5.2 测试要求

#### 5.2.1 测试回归
- 每次迭代完成后必须进行测试回归
- 运行所有自动化测试用例
- 验证功能正常和性能达标

#### 5.2.2 问题修复
- 发现问题必须及时修复
- 修复后必须重新测试
- 确保没有引入新问题

#### 5.2.3 测试用例维护
- 定期更新测试用例
- 确保测试用例与需求一致
- 添加新的测试场景

#### 5.2.4 测试文档管理

##### 迭代初始测试文档
- **测试用例统一文档**：维护所有已有的测试用例，包含测试场景、测试步骤、预期结果等信息
- **测试用例评估**：评估迭代变更对测试用例的影响，包括需要新增、调整或删除的测试用例

##### 迭代完成测试报告
- **测试用例变更记录**：记录本次迭代中新增、调整或删除的测试用例
- **测试结果统计**：记录测试用例的通过/失败情况，计算通过率
- **失败用例分析**：分析失败原因，记录修复过程和次数
- **测试过程信息**：记录测试执行过程中的关键信息

##### 测试文档命名规范
- 测试用例统一文档：`{迭代文档名称}_test_cases.md`
- 测试报告：`{迭代文档名称}_test_report.md`

##### 测试文档位置
- 测试文档与迭代文档放在同一目录，保持1:1映射关系
- 例如：`docs/iteration/2026-02/2026-02-14-task-list-preview-merge_test_cases.md`
- 例如：`docs/iteration/2026-02/2026-02-14-task-list-preview-merge_test_report.md`
